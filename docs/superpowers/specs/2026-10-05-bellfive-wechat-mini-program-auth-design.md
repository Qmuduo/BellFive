# BellFive 微信小程序与账号系统设计

## 目标

让 BellFive 能作为微信小程序运行，同时保留现有 Expo 手机端和 Web。小程序完整支持现有单机和好友房玩法。用户在 Expo/Web 使用用户名和密码注册登录；小程序使用微信身份登录，首次登录自动建档，并可绑定已有账号或为微信账号设置用户名密码，使同一账号的昵称、头像在各端同步。

## 当前项目背景

- 客户端使用 Expo Router、React Native、TypeScript 和 Zustand。当前入口承载单机、公开房间大厅、好友房、准备开局和重赛等状态。
- 游戏规则在 `src/game/`，WebSocket 消息和快照类型在 `src/network/`。
- `server/` 是 Node.js + TypeScript 房间服务。完整对局与公开房间列表保存在进程内，服务重启会清空。
- 昵称与头像目前只在客户端持久化。服务端房间收到客户端提供的昵称头像，没有用户账号或持久用户表。
- 客户端使用 Expo Audio、Haptics 和 Reanimated；这些 API 不构成可直接生成微信小程序 UI 的通用层。

## 范围

### 包含

- 新建独立的 Taro/React 微信小程序客户端，不迁移或替换现有 Expo 客户端。
- 通过共享现有纯游戏规则、牌组数据、游戏类型和网络协议，完成小程序全功能界面。
- 新增持久化账号服务：微信小程序登录、首次自动注册、用户名密码注册登录、账号绑定、会话和跨端资料同步。
- 保护现有单机离线游玩路径；游客可玩单机，线上大厅与好友房需要登录。
- 房间 WebSocket 连接使用账号会话认证，玩家资料由服务端账号数据决定。

### 不包含

- 排行榜、历史战绩、好友社交图谱、聊天、支付和运营后台。
- 房间、牌局及对局历史持久化。好友房继续使用现有进程内存储和生命周期。
- 手机短信、邮箱验证或邮箱找回。首期用户名密码找回仅对已绑定微信身份的账号开放。
- 把 Expo UI 全量迁移至 Taro，或用 WebView 嵌入现有 Web 页面代替小程序客户端。

## 方案选择

### 推荐：独立 Taro 小程序端，共享业务逻辑

保留现有 Expo 原生端与 Web，在仓库增加 `miniprogram/` Taro/React 客户端。Taro 使用微信小程序组件与平台 API；客户端复用 `src/game/` 的纯规则、共享类型与协议。Taro 编译配置显式纳入仓库共享目录。小程序的页面、导航、动画、音效、震动、存储和 WebSocket 适配单独实现。

这条路线隔离平台差异，同时保留已完成的 Expo 界面和原生能力。Taro 官方文档支持编译微信小程序，并提供 monorepo 外部目录的编译配置。

### 全前端迁移至 Taro

可逐步减少部分界面重复，但会重做 Expo 当前的动画、音效、存储与导航，并让现有移动端承担迁移风险。首期不采用。

### WebView 封装

可少写一套界面，但不能自然复用小程序页面组件和微信原生交互，完整游戏手感与微信登录流程也更难维护。首期不采用。

## 系统结构

### Expo 手机端与 Web

- 在现有房间入口提供注册、登录和退出账号入口。
- 使用用户名和密码访问同一账号服务。
- 保留游客单机；房间大厅、建房和加入房间先完成认证。
- 账号登录后以服务端昵称和头像为准。新注册时可以把已有本机资料作为初始资料；之后的资料编辑保存至服务端，并在再次登录时同步至本机。

### 微信小程序端

- 独立 Taro/React 工程，采用微信小程序组件实现入口、设置、公开大厅、房间码加入、等待审批、准备、牌桌和重赛界面。
- 单机可以游客方式运行。进入大厅或好友房时调用 `wx.login` 并把临时 code 交给服务端；首次微信登录自动创建用户档案。
- 如果该微信身份已绑定账号，服务端直接恢复对应账号。
- 若玩家已有 Expo/Web 用户名账号，可在小程序中输入该账号凭据并绑定当前微信身份。微信新用户也可在小程序给自己的账号设置用户名和密码，以便在 Expo/Web 登录。
- 房间分享使用微信小程序分享能力；游戏音效、轻量动画和震动使用小程序端适配。不可用的反馈能力应优雅降级，不影响牌局规则。

### 共享业务逻辑

- `src/game/` 中的游戏规则和牌组内容保持平台无关。
- 将微信运行时适配放在小程序专属目录，不从共享游戏规则直接导入 Expo 或 `wx` API。
- 共享房间协议允许账号认证建立连接上下文；房间动作继续按服务端权威规则处理。

### 服务端和存储

- 扩展当前 Node 服务，保留既有 WebSocket 房间管理并增加 HTTP 账号接口。
- 使用 SQLite 持久化用户、用户名凭据、微信身份绑定、用户资料和服务端会话。数据库文件路径可通过环境变量设置；部署时必须使用持久磁盘。
- 用户记录使用内部稳定 ID；用户名唯一；微信身份以小程序 AppID 与 `openid` 组成唯一键。若未来需要多个微信生态应用之间自动打通，可另行加入 UnionID 方案，但本期绑定依赖 BellFive 账号凭据，不要求开放平台应用绑定。
- 密码使用每用户随机盐和 Node.js 内置 `crypto.scrypt` 派生后保存，不保存明文。会话使用高熵随机令牌，数据库只保存令牌摘要与到期时间。
- 微信小程序 AppSecret 只存在服务端环境变量，不能放进小程序产物、Expo bundle 或 Web 客户端。
- WebSocket 首条认证消息验证会话，并将连接绑定到服务端解析出的用户 ID。房间创建、加入或资料更新不得信任客户端直接声明的玩家账号、昵称或头像。

## 账号流程

### Expo/Web 用户名账号

1. 注册时提交用户名、密码和可选的本机昵称/头像初值。
2. 服务端检查输入、用户名唯一性，保存密码派生结果并创建会话。
3. 登录时只返回通用凭据错误，避免透露用户名是否存在。
4. 已登录用户可更改昵称和头像；服务端资料是已注册账号的权威资料。

### 微信登录与首次自动建档

1. 小程序调用 `wx.login` 获取临时 code。
2. 小程序通过 HTTPS 把 code 交给 BellFive 服务端；服务端使用保密的 AppID/AppSecret 向微信换取用户标识。
3. 若微信身份已有绑定，服务端恢复对应 BellFive 账号；否则创建新账号并返回会话。
4. 微信登录使用平台身份识别用户，不请求昵称、头像等额外微信资料授权。玩家可使用 BellFive 内的昵称与头像设置。

### 账号绑定与凭据补充

- 对一个已存在的 BellFive 用户，可以在小程序中用用户名和密码重新验证，再把当前微信身份绑定到该用户。
- 对一个只有微信身份的用户，可以在小程序添加唯一用户名和密码；这只为同一个用户增加一种登录凭据，不创建第二个用户。
- 若微信登录已经自动创建了仅含昵称头像的账号，随后要绑定到一个已存在的用户名账号，必须再次验证目标账号密码并明确确认。服务端事务把微信身份转至目标用户，吊销临时账号会话，并以目标账号资料为准。由于本期没有战绩或房间历史，不迁移对局数据。
- 如果微信身份已关联到另一个含用户名凭据的账号，或用户名已占用，服务端拒绝绑定并返回清楚的下一步提示；不能静默覆盖或合并已有凭据。
- 只有已绑定微信的账号可以通过重新验证微信身份重设密码。未绑定微信的账号首期没有自动找回渠道。

## 接口与数据流

服务端至少提供以下账号操作：

- `POST /auth/register`：注册用户名、密码和初始资料。
- `POST /auth/login`：验证用户名密码并创建会话。
- `POST /auth/wechat/login`：兑换小程序 code，登录已绑定身份或首次自动建档。
- `POST /auth/wechat/link`：验证 BellFive 账号密码并绑定/迁移当前微信身份。
- `POST /auth/credentials`：给当前登录的微信账号增加用户名与密码。
- `GET /auth/me` 与 `PATCH /auth/me/profile`：读取、更新当前账号和昵称头像。
- `POST /auth/password/reset/wechat`：通过已绑定微信身份验证后更新密码。
- `POST /auth/logout`：撤销当前会话。

HTTP 认证接口统一返回经过校验的内部用户 ID、账号资料和不透明会话令牌。客户端将令牌存储在对应平台的持久存储适配器中；每次重新安装或会话过期时按登录流程恢复。WebSocket 认证失败时拒绝房间动作，并要求用户重新认证。

好友房创建和加入仍接受房间码、准备、翻牌、抢铃、离开与重赛意图；服务端从 WebSocket 的已认证连接得到玩家身份与资料。游客本地单机不依赖账号服务器。

## 错误处理

- 微信 code 失效：返回可识别的认证错误，由小程序重新调用 `wx.login` 后重试。
- 微信认证密钥未配置或微信服务不可用：账号/线上房间显示明确错误；访客单机仍可运行。
- 用户名重复、密码格式错误、账号凭据错误、绑定冲突和会话过期：返回清晰且不泄漏密码或服务端密钥的提示。
- 数据库不可用：拒绝账号和在线服务请求，不把身份或资料静默写到本地冒充成功。
- WebSocket 会话无效或过期：拒绝在线操作，回到登录入口后可重新认证。
- 客户端不得记录密码、AppSecret、临时微信 code 或完整会话令牌。

## 验证方案

- 分别构建和类型检查 Expo/Web、服务端及 Taro 微信小程序端。
- 使用微信开发者工具和已配置的小程序测试账号验证首次建档、重复登录、微信账号与用户名账号绑定、密码找回及冲突提示。
- 跨端验证同一账号的昵称头像读写；登录不同账号时资料不能串用。
- 保留并验证访客单机可在账号服务不可用时运行。
- 两个小程序或 Expo/Web 客户端完成公开大厅、申请/审批、房码加入、双方准备、实时对局和重赛。
- 验证 WebSocket 缺少、错误和过期会话不能创建房间、加入房间或执行游戏动作。
- 真机微信认证依赖用户的小程序 AppID/AppSecret、备案/配置的 HTTPS 请求域名和 WebSocket 合法域名；在这些外部条件具备前，真实微信登录不能作为已验证完成。

## 实施顺序

1. 建立持久账号数据模型、凭据校验、会话管理和认证 HTTP 接口。
2. 给现有 Expo/Web 增加注册、登录、资料同步和线上房间认证，保留游客单机。
3. 调整共享网络协议与房间服务，使在线玩家身份和资料来自认证会话。
4. 建立 Taro 微信小程序工程与共享源码编译配置，接入微信登录、自动建档和绑定。
5. 按现有流程完成小程序入口、大厅、好友房、单机、准备、牌桌、反馈与重赛。
6. 按验证方案检查跨端账号资料和完整线上玩法；真实微信联调使用小程序凭据与正式配置域名。
